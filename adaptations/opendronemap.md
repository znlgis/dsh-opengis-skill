## DeepSeek Harness 使用建议

- **加载与引用**：单文件技能，没有 reference 目录；正文「核心命令」的参数表与预设组合是主要入口，「典型工作流」四条链路按场景取用，「常见问题」表先对症状。成果入库转换用 `skill` 加载 `gdal`，点云清洗用 `pdal`，三维发布用 `cesiumjs`；不要 `read` 兄弟目录的 SKILL.md。
- **执行环境**：全部命令在 `ops_bash` 里跑，Windows 侧依赖 Docker Desktop，动手前确认守护进程在跑（`docker info` 能出 Server 段）。正文的 `docker run -ti` 在 DSH 里会因无 TTY 报 `the input device is not a TTY`，去掉 `-t` 只留 `-i` 或直接不加；MSYS bash 会把 `-v /datasets:/datasets` 这类参数当路径改写，挂载统一写成宿主 `-v /d/datasets:/datasets` 并在命令前加 `MSYS_NO_PATHCONV=1`，或改用 `pwsh` 调 `docker run -v d:/datasets:/datasets`。整条流水线以小时计、镜像首次拉取就上 GB，必须 `run_in_background` 起作业、`job_output`（可带 `wait`）收进度与末尾日志，跑错再 `job_kill`，不要在一条前台命令里等完。
- **先探测版本**：`docker --version` 与 `docker info --format '{{.MemTotal}}'` 先看引擎与可用内存（OOM 是头号失败原因），`docker run --rm opendronemap/odm:3.6.2 --version` 确认镜像标签是正文写的 3.6.2 而不是 `latest`，第一次会先拉镜像，同样放后台。WebODM 侧 `curl -s http://localhost:8000/api/` 应返回带 version 的 JSON，起 `./webodm.sh` 前先 `curl -s -o /dev/null -w '%{http_code}' http://localhost:8000/` 看端口有没有被占。
- **验证产物**：先数输入 `ls images | wc -l` 与预计张数一致，再看退出码——137 就是 OOM，别当普通失败。产物按正文目录约定逐项核：`gdalinfo -json odm_orthophoto/odm_orthophoto.tif` 核对 CRS 与尺寸、`gdalinfo -stats odm_dem/dsm.tif` 看高程范围是否合理，`odm_report/` 里的重叠度与重投影误差才是质量判据，只出图不代表成果可信。要肉眼确认正射影像，用 OSGeo4W 的 `gdal_translate -of PNG -outsize 1024 0 odm_orthophoto.tif preview.png` 生成缩略图后 `read_image` 看一眼，纯白或被裁成一条与空文件同罪；WebODM 的成果最终由用户在 2D/3D 查看器确认，写明「打开哪个地址、应看到什么」。
- **风险与权限**：`--rerun` 会就地重算并覆盖已有阶段产物、`./webodm.sh down` 删容器、`docker system prune` 清镜像层，都不可逆，执行前用 `ask_user_question` 给「换项目目录重跑/覆盖现有成果/取消」；WebODM 的 `admin` 密码与 JWT token 从环境变量传入、命令里只引用 `$TOKEN`，日志与回答里不回显。对外暴露 8000/3000 端口、上传航拍影像、把成果传给第三方之前，确认数据合规（测绘资质与隐私）。
- **常见失败**：`No images found` 是缺 `images/` 子目录或 `--project-path` 传成了数据集本身；空三大量未注册先查重叠度与糊片，改参数救不回来；正射空白或被裁条先去 `--auto-boundary` 再试；没有 `dsm.tif` 是没传 `--dsm`；Windows 挂载失败基本是路径写了反斜杠或 Docker Desktop 没共享该盘符。
